# notion-style-design-spec-md-to-html

## 中文名

Notion 风设计规格 Markdown 转 HTML

## 定位

把一份已经结构化的 Markdown 设计文档，转成一种偏 Notion 风、产品规格说明书感很强的单文件 HTML。

它和“报告 / 交接文档”是同一大类输出，但重点不同：

- 更强调设计规格、模块拆分、实现说明
- 更适合前后端协作、产品设计、联调契约
- 更像规范文档，而不是进展报告

## 适合

- PRD 拆解后的设计说明
- H5 / Admin / Backend / Edge 的对接规格
- 模块级实现设计文档
- API 契约说明
- 实施顺序和改动边界文档

## 不适合

- 周报、复盘、交接报告
- 长篇叙事性文章
- 营销页、官网、海报
- 只想把 Markdown 原样渲染出来的场景

## 输出目标

输出应满足以下条件：

- 单文件 HTML，可直接打开
- 视觉上接近 Notion 风技术文档，而不是博客文章
- 左侧支持两级目录
- 顶部有标题、eyebrow 和 meta-grid
- 代码块带语言和文件名头部
- 支持 tree、badge、card-grid、steps、callout、table
- 移动端自动降级为单栏

## 推荐输入

- 原始 Markdown 文件
- 文档标题
- 版本号或阶段号
- 涉及端 / 模块
- 文档日期
- 是否保留 API 契约、代码片段、文件改动表、实施顺序

如果用户没有补充说明，默认它是一份“面向研发协作的设计规格说明”。

## 工作方式

1. 先完整阅读 Markdown，识别主章节和子章节。
2. 判断这份文档是否属于“规格说明体裁”，而不是“报告体裁”。
3. 一级目录通常来自核心章节，二级目录通常来自关键子模块或子功能。
4. 用 [assets/design-spec-template.html](skills/writing/notion-style-design-spec-md-to-html/assets/design-spec-template.html) 作为骨架。
5. 需要把内容映射到更明确的组件：
   - 文档头信息 → `header + meta-grid`
   - 范围边界 / 模块树 → `tree`
   - 文件改动 → `tbl-wrap > table`
   - 实现代码 / API 代码 → `code-block`
   - 状态或新增项 → `badge`
   - 并列说明方案 → `card-grid`
   - 提醒或待确认 → `callout`
   - 实施顺序 → `steps`
6. 代码片段优先保留“语言 + 文件名 + 核心片段”的规格说明语气。
7. 最终输出成单文件 HTML，并验证目录、锚点和移动端阅读体验。

## 版式规则

- 左侧目录更像知识库导航，而不是轻文档目录。
- 目录允许二级缩进，适合 `2.1 / 2.2 / 3.1 / 3.2` 这类规格拆分。
- 顶部 header 要先交代文档身份，再进入正文。
- `h2` 是一级模块边界，`h3` 是关键子功能，`h4` 常用于“文件改动”“补充说明”。
- 表格和代码块都要尽量规整，像规范文档，不要像随手笔记。
- 可以使用少量 badge 标出“新增”“改动量大”“收尾”等语义。
- 整体气质克制、干净、结构优先。

## 内容转译原则

- 不要把 Markdown 直接变成普通 article 页面，这会损失“规格文档”的导向性。
- 顶部应优先抽出版本、PRD、涉及端、日期、实施顺序等 meta 信息。
- 如果文档里存在“改动范围”或“模块边界”，优先转成 tree，而不是普通列表。
- 代码块应尽可能带文件名和语言标签，体现“这是设计落点”。
- “新增”“优先启动”“收尾”“颜色区分”这类信息适合 badge 化。
- 并列动作说明、ActionSheet 类型或方案对照，优先转成 card-grid。
- 如果文档结尾有实施顺序、推进顺序、分阶段实施建议，优先转成 steps。
- 如果有很多 `2.1 / 2.2 / 3.1 / 3.2` 子节，目录中应显式保留二级项。

更细的组件映射见 [references/component-map.md](skills/writing/notion-style-design-spec-md-to-html/references/component-map.md)。

## 禁忌

- 不要做成营销感、封面感很强的页面。
- 不要用高饱和渐变、玻璃拟态、大阴影卡片。
- 不要删掉代码块、文件路径、API 契约，只保留摘要。
- 不要把目录弱化到只能看一级章节。
- 不要让代码块失去“文件名 + 语言”头部。
- 不要为了酷炫而加复杂动画；目录高亮这类功能性脚本可以保留。

## 交付检查

- 顶部 header 信息是否完整
- 一级 / 二级目录是否和正文锚点一致
- tree、table、code-block 是否都完整
- 代码块是否有语言和文件名头部
- badge 是否只用于真正有语义的地方
- 实施顺序是否适合转成 steps
- 小屏下目录是否自动下移为顶部区域
- HTML 是否仍是单文件

## 常用提示词

按 `notion-style-design-spec-md-to-html` 处理这个 Markdown：读取文档结构，保留模块边界、文件改动、代码片段、API 契约和实施顺序，输出为同风格单文件 HTML。需要有两级目录、header meta-grid、tree、带文件名的代码块、badge、steps 和移动端适配。

如果原始 Markdown 只是需求摘要，先帮我补出更像设计规格说明书的章节组织，再输出最终 HTML。
